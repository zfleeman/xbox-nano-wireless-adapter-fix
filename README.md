# Xbox Nano controller on the Xbox Wireless Adapter for Windows

The Xbox Nano controller pairs with Microsoft's own Xbox Wireless Adapter for Windows (USB ID `045E:02FE`), but Windows won't let it connect. The controller's light blinks forever, and no controller ever shows up in Windows. The same controller and adapter work on Linux.

This repo is a proof-of-concept workaround: **xdongle**, a small program written in Python that replaces Microsoft's driver for the adapter. It talks to the adapter's radio and the controllers directly, the way the Linux driver [`xone`](https://github.com/dlundqvist/xone) does, and presents each controller to Windows as a virtual Xbox 360 controller that every game understands.

It's meant for people who want to use hardware they already bought, and as a starting point others can adapt. It isn't affiliated with Microsoft, and it isn't a polished product. Read [What changes on your PC](#what-changes-on-your-pc) before installing, and keep [Undo](#undo) handy.

## Why Windows rejects the controller

When a controller connects through the adapter, Windows' Xbox controller driver (`xboxgip.sys`) runs an authentication check with the controller. The Nano fails that check on Windows, and the driver disconnects it. The controller reconnects about 4.6 seconds later and fails again, forever. That's the blinking light. A trace of Microsoft's driver shows each attempt:

```
DeviceConnected     PID=0x0B4C (Xbox Nano)
DeviceSecurity      SecurityPass=0  SecurityIterations=5
DeviceDisconnected  Reason=3
```

Linux works because `xone` runs the same handshake but doesn't disconnect controllers that fail it. There's no registry setting, driver update, or Windows setting that turns the check off (as of `xboxgip.sys` 10.0.26100.9818). [INVESTIGATION.md](INVESTIGATION.md) has the full evidence, what was ruled out, and how to check whether a Windows update has fixed it.

## How the fix works

```
Controller --radio--> Xbox Wireless Adapter --USB (WinUSB driver)--> xdongle --> ViGEmBus --> virtual Xbox 360 controller --> games
```

1. **WinUSB instead of Microsoft's adapter driver.** [Zadig](https://zadig.akeo.ie) switches the adapter from Microsoft's driver (`mt7612US.sys` plus `xboxgip.sys`) to WinUSB, Microsoft's generic USB driver. WinUSB lets a normal program send USB commands to the device. This only affects the adapter: controllers plugged in by USB cable keep using Microsoft's driver.
2. **xdongle runs the adapter.** At start it uploads the adapter's firmware into the adapter's RAM (the same firmware file Microsoft's driver uses, copied from your Windows driver store), sets up the radio, and then handles pairing and the Xbox controller protocol (GIP). It runs the authentication handshake like `xone` does, but keeps the controller connected if the handshake fails.
3. **ViGEmBus makes the virtual controller.** [ViGEmBus](https://github.com/nefarius/ViGEmBus) is a signed kernel driver that creates virtual game controllers. xdongle creates one virtual Xbox 360 controller per real controller and copies the buttons, sticks, and triggers into it. Rumble from games goes back to the controller.

**No drivers are patched.** Microsoft's drivers were traced and studied, not modified. They stay installed, and putting the adapter back on them is the [Undo](#undo) step.

What doesn't change:

- **No Microsoft files are modified or deleted.** Microsoft's adapter driver stays in the Windows driver store, ready for Undo.
- **Nothing is written to the adapter's or the controllers' permanent memory.** The firmware goes into the adapter's RAM and is gone when it loses power. xdongle only reads the adapter's one-time-programmable memory, for its radio address and per-channel power settings. Pairings are kept, so the adapter and controllers keep working with an Xbox, Microsoft's driver, or Linux.
- **xdongle doesn't use the network, edit the registry, or install services.** It runs as your user account at "above normal" priority (see [Latency](#latency)).

The Python packages are pinned to exact versions with SHA-256 hashes, so pip refuses any file that doesn't match:

| Package | Why |
|---|---|
| `libusb1` (with its bundled `libusb-1.0.dll`) | Sends USB commands to the adapter through WinUSB. |
| `cryptography` (plus `cffi` and `pycparser`) | The authentication handshake's RSA, ECDH, and HMAC math. |
| `vgamepad` (with its bundled `ViGEmClient.dll`) | Talks to ViGEmBus to create the virtual controllers. |

One thing to know about `vgamepad`: it's only published as source code, and its `setup.py` launches its own bundled ViGEmBus installer (an older version, 1.17.333) if it doesn't find ViGEmBus. It looks for ViGEmBus under an old name, so it misses current versions. `install.ps1` sets `VGAMEPAD_SKIP_VIGEMBUS_INSTALL=true` so that doesn't happen. If an installer window appears anyway, close it.

## What xdongle's code does

About 2,400 lines of Python in `xdongle/`, ported from `xone` (and its predecessor `xow`):

| File | What it does |
|---|---|
| `__main__.py` | Startup: finds the adapter firmware (and checks its SHA-256), sets up logging, makes sure only one copy runs, and restarts the adapter if it's unplugged. |
| `usbdev.py` | Opens the adapter through libusb/WinUSB and keeps reads queued on its two incoming USB endpoints. |
| `mt76.py` | Drives the adapter's MediaTek MT76x2U radio chip: firmware upload to RAM, radio and channel setup, and the per-controller link keys. |
| `dongle.py` | Pairing (the adapter's button), controllers connecting and disconnecting, and turning radio frames into controller messages. |
| `gip.py` | The Game Input Protocol: identifying the controller, power and LED commands, rumble, and turning input reports into Xbox 360 controller state. |
| `auth.py` | The authentication handshake (RSA and ECDH variants). Like `xone`, it doesn't check the controller's certificate. When the handshake succeeds, the link is encrypted. When it fails (the Nano), xdongle logs it and keeps going. |
| `vpad.py` | The virtual Xbox 360 controller, through `vgamepad`. |

`tests/test_offline.py` tests the protocol code without any hardware. `tests/latency_bench.py` measures xdongle's input delay with real virtual controllers but no adapter.

## Requirements

- Windows 10 or 11, 64-bit.
- The Xbox Wireless Adapter for Windows, the current small model with USB ID `045E:02FE`. Plug it in once before you start, so Windows installs Microsoft's driver. That puts the firmware file xdongle needs in the driver store. The older, larger adapter (`045E:02E6`) isn't supported.
- [Python 3.12 or newer](https://www.python.org/downloads/windows/) from python.org (includes the `py` launcher).
- [ViGEmBus 1.22.0](https://github.com/nefarius/ViGEmBus/releases/tag/v1.22.0) (`ViGEmBus_1.22.0_x64_x86_arm64.exe`). If you already have 1.21.442, keep it: the driver is the same.
- [Zadig](https://zadig.akeo.ie) (a single `.exe`, nothing to install).

## Install

1. **Install Python and ViGEmBus** from the links above.
2. **Get this repo**: `git clone https://github.com/zfleeman/xbox-nano-wireless-adapter-fix`, or download it as a ZIP and extract it. Put it somewhere permanent, like `%USERPROFILE%\apps\xbox-nano-wireless-adapter-fix`, since the Startup shortcut points at it.
3. **Switch the adapter to WinUSB with Zadig.** Run Zadig (it asks for admin). Choose Options > List All Devices, pick the adapter in the dropdown (it shows up as "XBOX ACC" or "Xbox Wireless Adapter for Windows"), and check that the USB ID reads `045E 02FE`. Pick **WinUSB** as the target driver and click **Replace Driver**. From now on, the adapter is listed under "Universal Serial Bus devices" in Device Manager, and Windows' own Xbox driver no longer sees it.
4. **Run the installer** from PowerShell in the repo folder (no admin needed):

   ```
   powershell -ExecutionPolicy Bypass -File install.ps1
   ```

   It checks for Python and ViGEmBus, creates `.venv` with the hash-checked packages, checks that the adapter uses WinUSB, then adds the Startup shortcut and starts xdongle hidden. Add `-NoAutostart` to skip the last part and run xdongle by hand with `run-xdongle.cmd` instead.

The first time xdongle starts, it copies `FW_ACC_00U.bin` from Microsoft's adapter driver in `C:\Windows\System32\DriverStore\FileRepository\mt7612us_rl.inf_*` into `xdongle\firmware\`, and only accepts it if its SHA-256 is `48084d9fa53b9bb04358f3bb127b7495dc8f7bb0b3ca1437bd24ef2b6eabdf66`. The file belongs to Microsoft and isn't in this repo. If your driver store doesn't have it, download [Microsoft's driver package from the Update Catalog](https://catalog.s.download.windowsupdate.com/c/msdownload/update/driver/drvs/2017/07/1cd6a87c-623f-4407-a52d-c31be49e925c_e19f60808bdcbfbd3c3df6be3e71ffc52e43261e.cab) (the same file `xone` uses), extract the file with `expand -F:FW_ACC_00U.bin <file>.cab .`, and save it as `xdongle\firmware\02fe_FW_ACC_00U.bin`. xdongle checks its SHA-256 at every start.

## Use

- **Controllers that are already paired** connect when you turn them on. There's also a 60-second pairing window every time xdongle starts.
- **To pair a new controller**, press the button on the adapter, then hold the pair button on the controller until its light blinks fast.
- Each controller shows up as an "Xbox 360 Controller for Windows" (up to 16).
- `run-xdongle.cmd` runs xdongle in a console window instead, which is handy for testing. `--debug` logs the protocol, and `--trace-input` logs every input report. Stop the hidden copy first with `autostart.ps1 -Disable`, because only one copy can use the adapter. Ctrl+C turns connected controllers off and exits.
- `xdongle.log` in this folder records connections, pairing, battery level, and errors. It rotates at 5 MB and keeps two old files.

## Undo

Each step undoes one row of [What changes on your PC](#what-changes-on-your-pc). Steps 2 and 3 need an admin PowerShell. They use standard Windows tools, but haven't been run start to finish for this repo yet. If something doesn't match what you see, please open an issue.

1. **Stop xdongle and remove the Startup shortcut:** `powershell -ExecutionPolicy Bypass -File autostart.ps1 -Disable`
2. **Put Microsoft's driver back on the adapter.** List the driver packages with `pnputil /enum-drivers` and find the one with Provider Name `libwdi` and Original Name `xbox_acc.inf` (the `.inf` is named after the device, so yours may differ). Note its Published Name, e.g. `oem76.inf`. Then remove it, which also takes it off the adapter:

   ```
   pnputil /delete-driver oem76.inf /uninstall
   ```

   Unplug the adapter and plug it back in. Windows installs Microsoft's driver again from the driver store, and the adapter is back under "Network adapters" in Device Manager as "Xbox Wireless Adapter for Windows". In Device Manager, you can also right-click the adapter under "Universal Serial Bus devices", choose Uninstall device, and tick "Attempt to remove the driver for this device".
3. **Remove Zadig's certificate:**

   ```
   Get-ChildItem Cert:\LocalMachine\Root, Cert:\LocalMachine\TrustedPublisher |
       Where-Object Subject -eq 'CN=USB\VID_045E&PID_02FE (libwdi autogenerated)' | Remove-Item
   ```

4. **Delete this folder.**
5. **Optional:** uninstall ViGEmBus and Python in Settings > Apps if nothing else uses them.

## Troubleshooting

Look in `xdongle.log` first.

- **"Waiting for the Xbox Wireless Adapter (WinUSB driver)"** means the adapter isn't plugged in, or it's still on Microsoft's driver. Check Device Manager.
- **"Found adapter ... could not open it ... Is the WinUSB driver installed"** usually means Windows put Microsoft's driver back on the adapter, which a big Windows update can do. Do the Zadig step again.
- **"is in use by another program"** means another copy of xdongle has the adapter. `autostart.ps1 -Disable` stops the hidden one.
- **No log and no controller after logging in:** run `run-xdongle.cmd` in a console to see the error.
- **After upgrading or removing Python**, delete `.venv` and run `install.ps1` again.

## Limits

- **Windows sees an Xbox 360 controller,** so there's no Share button, no impulse-trigger rumble, and no battery level in Windows (it's in the log).
- **No headset audio** through the controller.
- **The Xbox Accessories app can't see controllers on the adapter.** Use a USB cable for firmware updates and button remapping. USB-connected controllers still use Microsoft's driver.
- **The Nano's link isn't encrypted,** because encryption keys come from the authentication handshake, which the Nano fails. Controllers that pass it (like the Xbox Series controller) get an encrypted link, as with Microsoft's driver.
- **Only tested with** the Xbox Nano and Xbox Series controllers. Other Xbox One and Series controllers should work, since the protocol is the same, but they aren't tested.

## Latency

`tests/latency_bench.py` feeds input reports through the real code into a real virtual controller. From a report arriving over USB to Windows seeing the new controller state, xdongle takes about 0.1 ms in the middle case and under 1 ms in the worst case, even with every CPU thread at 100%. That's why it runs at "above normal" priority: at normal priority, a fully loaded CPU caused occasional delays of up to 19 ms. For comparison, one frame at 144 fps is 6.9 ms. xdongle is idle almost all the time, so the higher priority doesn't slow down other programs.
